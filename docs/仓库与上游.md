```powershell

git log --oneline main..upstream/main   # 先看上游多了什么
```

> 本仓库的价值主要来自 **18 个跨内核兼容提交**（`settingsScope` 兜底、图标双代解析、

> ```powershell

> 完整的改动清单见 [`DSH Desktop × Fairy 兼容性适配报告.pdf`](<DSH Desktop × Fairy 兼容性适配报告.pdf>)（10 类故障逐条对应提交号）。

>
> **实测结论（2026-10-04）**：`Set-SettingsMerge` 已经与代码脱节，**跑不通且不安全**：
>
> | 失败形态 | 实测证据 |
> | --- | --- |
> | **voice 直接抛错** | `诊断通道锚点匹配数不为 1` —— 该锚点在上游原件 `upstream-originals\fairy-voice-client.js` 中**存在 0 处匹配**，脚本从上游结构漂移后就再没同步过 |

>
> **因此当前的正确做法是**：
> 1. **不要**重新生成。改 `client.js` 请**外科手术式精确替换**，并逐处核对 `git diff`。
> 2. 同步修改生成器里的**对应模板片段**（`lib/settings-merge.ps1` 里那 6 处 URL、

> 4. 任何编辑后按 §3.1 检查 `.ps1` 的 BOM 与 `git diff`，确保编辑工具没破坏文件。
>
> **将来若要修复生成器**，工作量是：把 8 个兼容提交对 `client.js` 的改动
> 回填进生成器模板，或重建一份**含兼容修复的 `upstream-originals` 原件**，
> 然后用 `git diff` 断言"重新生成 == 当前提交版本"**逐字节相等**才算修好。

### 3.1 ⚠ 编辑后必须校验编码（本仓库踩过两次）

`.gitattributes` 规定 `.ps1` / `.cmd` / `安装说明.txt` 为 `-text`（**原样存取，不做行尾归一化**），
而 PowerShell 5.1 与本机 936 代码页**靠 BOM 判定编码**。于是：

| 症状 | 后果 |
| --- | --- |
| `.ps1` **丢掉 BOM** | PowerShell 按 GBK 解码，中文注释全变乱码（`鍚堝苟`），**脚本直接解析失败** |
| 非 `-text` 文件**被加上 BOM** | 与仓库内格式不符，产生无意义 diff |
| 换行被工具改写 | 见下面的"不要做"一节 |

**普通编辑器（含多数 AI 编辑工具）会在保存时剥掉 BOM。** 所以每次批量编辑后**直接检查字节**，
不要依赖任何自动工具：

```powershell
# 1) 所有 .ps1 都必须带 BOM（缺一个都说明编辑工具破坏了它）
git ls-files "*.ps1" | ForEach-Object {
  $b = [System.IO.File]::ReadAllBytes((Join-Path (Get-Location) $_))
  if (-not ($b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF)) { "缺少 BOM: $_" }
}

# 2) 真实变更清单（这是唯一权威判据）
git status --short
git diff --stat
```

> 🔴 **`.cmd` 不带 BOM 是设计，不是缺陷。** 本仓库的 `.cmd` 一律是**纯 ASCII 启动器**
> （一个中文字都没有，中文全放在同名的 `.ps1` 里）—— 正因如此它们才在 936 代码页上绝不会乱码。
> 曾有一个自制的"编码守卫"脚本把这一点误判为"缺失 BOM"并试图"修复"，
> 所以那个脚本已被删除。**看到 `.cmd` 没有 BOM，不要动它。**

> 🔴 **不要对全树做换行归一化。** `.gitattributes` 里 `* text=auto` 意味着
> git 内部存 LF、而这台机器检出成 CRLF，这是**正常且干净**的状态
> （`git status` 不会因此报变更）。早期一个自制脚本按"应该全是 LF"去改写，
> 一次动了 189 个文件。**换行被弄乱时，唯一正确的修法是 `git checkout -- <路径>`。**

> 📌 真实事故记录：本次修订中，一次 URL 替换就让 `lib\settings-merge.ps1` 丢了 BOM，
> 使该脚本**当场无法解析**。修复方式就是把 BOM 加回去（`UTF8Encoding($true)` 重新写入）。
> 仓库里 `install.cmd` / `install_full.cmd` 的 UTF-16LE BOM 也曾被同型问题破坏（commit `e617f7a`）。

## 4. ⚠ 三个"结构性冲突点"（合并上游时一定会遇到）

这是本分支和上游结构不同造成的，**合并前请先读这一段**，否则容易把上游更新悄悄丢掉。

### 4.1 人设预设被移进了插件包

| | 位置 |
| --- | --- |
| 上游 | `.agent-presets/fairy/…`（仓库根） |
| 本分支 | `fairy-visual/dsh-fairy-visual/.agent-presets/fairy/…`（包内） |

**为什么移动**：`dsh plugin add` / npm / tarball 安装时只带一个包目录，预设放在插件包内才能
跟着包一起走（否则装到别的机器就丢了）。根目录 `.agent-presets/README.md` 是指路牌。

**后果**：上游更新人设语料时，git 会报 `deleted by us`（你删了它、它改了它）。
这时**不能"接受删除"就完事**——要手动把上游的新语料同步进插件包：

```powershell
git show upstream/main:.agent-presets/fairy/canon/fairy_canon.json > fairy-visual\dsh-fairy-visual\.agent-presets\fairy\canon\fairy_canon.json
# 其余文件同理，或整体取一次：
git checkout upstream/main -- .agent-presets/fairy
Copy-Item -Recurse -Force .\.agent-presets\fairy\* .\fairy-visual\dsh-fairy-visual\.agent-presets\fairy\
Remove-Item .\.agent-presets\fairy -Recurse -Force   # 根目录只留 README 指路牌
```

> 另外：上游的 `agent.cordis.yml` 里引用了作者私有的 `runtime/index.js` 与 `runtime/safety-gate.js`
> （这两个文件上游没发布），本分支已把这两条移除——同步时**这两条要保留移除状态**，否则预设又加载不了。

### 4.2 客户端 `client.js` 是**生成物**，不是上游原件

| 文件 | 来源 |
| --- | --- |
| `upstream-originals\fairy-visual-client.js` | 上游原件（**只读副本**） |
| `upstream-originals\fairy-voice-client.js` | 上游原件（**只读副本**） |
| `fairy-visual\…\lib\client.js` | 由 `lib/settings-merge.ps1` 生成（含设置栏合并 / 自检面板 / 通知行） |
| `fairy-voice\…\lib\client.js` | 由同一个脚本生成（去掉它自己的 settings.section + 诊断通道） |

**合并上游时最容易犯的错**：直接接受上游对 `lib\client.js` 的改动 —— 那会把你的设置栏补丁覆盖掉。

正确顺序：

1. `git checkout upstream/main -- <该包的 lib/client.js>` **先别直接接受**；
   把上游的新版另存为 `upstream-originals\fairy-visual-client.js`（原件位置）；
2. ~~重新运行 `Set-SettingsMerge -Mode merged -Force` 生成；~~
   🔴 **当前不可用 —— 见 §3 的红色警告。** 生成器已与产物脱节，
   重新生成会丢兼容修复（实测 visual 少 77 行）且 voice 直接抛锚点错。
   **现状下正确做法**：以 `lib/client.js` 为唯一事实来源，把上游的结构变化
   **手工合入产物**，再同步改生成器模板；
3. `node --check` 两个产物 —— **必做**；
4. 若将来修好生成器后它报「锚点匹配数不为 1」→ 说明上游改了结构，
   需要同步更新 `lib\settings-merge.ps1` 里的锚点（这正是当前 voice 侧的故障状态）。

### 4.3 每个插件包都改过 `package.json` 与 `lib/index.js`

本分支为了"单包可独立分发"做了三件事，合并时不要被上游覆盖回去：

- 各包新增 `cordis.patch.yml` + `dsh.bundle.patch`，让 `dsh plugin add` 一条命令就能装。

## 5. 分支与发布策略

```
main                你的发布线（永远可打包、可发群）
  ├─ feat/*         新功能（可选，做完合回 main）
  └─ v0.2.3         tag：一个可发布版本
```

发版流程：

1. 改仓库根 **`VERSION`** 文件（整理版版本号，会显示在设置页顶部）；
   **改动了哪些插件包，就把那些包的 `package.json` 的 `version` 往上加** ——
   `install.cmd` 与插件市场都靠「包版本」判断有没有更新；
   再更新 `README.md` / `RELEASE-NOTES.md`；
2. ~~重新生成客户端合并包（第 3 节命令）；~~ 🔴 **跳过这一步 —— 见 §3 红色警告**。
   生成器当前跑不通且会丢兼容修复；若这轮确实改了 `lib\client.js`，
   按 §3 的"精确替换 + `node --check` + 核对 `git diff`"流程处理，
   并同步更新 `lib\settings-merge.ps1` 里的对应模板；
3. `.\pack.ps1` → 产出 5 个 `.tgz`（文件名**不带版本号**，可直接上传）+ `install.cmd` + `SHA256SUMS.txt`；
4. `.\verify-isolated.ps1` 或 `tools\settings-probe.mjs` 跑一遍实测；
5. `git add -A; git commit -m "release: v0.x …"; git tag v0.x-compat.N; git push origin main --tags`；
6. 把**不带版本号的那 5 个 `.tgz`** 作为 GitHub Release 附件上传；
7. 发布公告（模板与红线见 `AGENTS.md` §8 —— **只推本仓库**，不要把用户引到孤舟版）。

> ⚠️ **本仓库的标签命名**：上游孤舟版用 `v0.3.8` 这类裸版本号；本仓库的兼容版发布用
> **`v0.3.8-compat.N`**（基线版本 + 兼容序号），避免与上游标签混淆。
> 当前发布标签即 `v0.3.8-compat.1`。
>
> ⚠️ **推送目标**：本地分支已与远端同名（`main`），无参数 `git push` 即可。
> 若将来又改了本地分支名，**务必显式写 `HEAD:main`**，别让 `git push origin <别的名字>` 悄悄开出一条新分支。

> ⚠️ 附件名**必须不带版本号**：README 与 `install.cmd` 里用的是
> `.../releases/latest/download/<包名>.tgz` 这种永久地址，而 `latest/download/` 的文件名是**照字面取**的 ——
> 带版本号的话，提交当天有效，下次发版就 404。
>
> 旧脚本（`install.ps1` / `uninstall.ps1` / `build-release.ps1` / `安装说明.txt` / `patches\`）
> 已全部挪进 `legacy\`，说明见 `legacy\README.md`。

> `release/` 与 `*.zip` 已在 `.gitignore` 里：**不要**把二进制包提交进历史，每次发版都会让仓库膨胀。
> 分发走 **GitHub Releases**（本仓库）与 **GitHub Release 页**（上游孤舟版另走 QQ 群，与本仓库无关）。

### ⚠ Release 附件必须用英文名

**GitHub 会把附件名里的中文吞掉**：`Fairy-DSH-v0.2.3-一键部署版-含依赖.zip` 上传后变成
`Fairy-DSH-v0.2.3-.-.zip`（实测，转义本身是对的，是 GitHub 侧清洗）。所以：

| 附件名（英文，GitHub 用） | 对应群文件（中文） |
| --- | --- |
| `Fairy-DSH-v0.2.x-deploy-with-deps.zip` | `Fairy-DSH-v0.2.x-一键部署版-含依赖.zip` |
| `Fairy-DSH-v0.2.x-lite.zip` | `Fairy-DSH-v0.2.x-一键安装版.zip` |

Release 正文里要写这张对照表，否则群友不知道下哪个。**本地打包文件名照旧用中文**（发给群友的就是那个）。

传给 GitHub 的 `name` 查询参数记得转义，且 PowerShell 里要用 `${url}?name=` 写法
